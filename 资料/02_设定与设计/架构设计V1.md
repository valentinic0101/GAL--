# 开放世界 GALGAME 架构设计 V1

- **依据**：《人物设定与关系总览.md》（人物圣经 v1.0）
- **日期**：2026-09-14
- **核心思路**：有限选项的人工故事线 → 故事背景 + 多 Agent 性格驱动 + 玩家自由输入 + 信息在社交网络上传播
- **一句话结论**：方向可行，且人物圣经已完成内容层的 80%；当前缺的是引擎层——世界状态、记忆、信息传播、调度。

---

## 一、可行性判断（有先行者，别从零摸索）

你要的东西学术上叫"生成式社交模拟 + 剧情驱动"，最直接的参照是 **Stanford 2023 的 Generative Agents（Smallville 小镇）**：25 个 Agent，各有性格、日程、记忆、反思机制，信息靠"八卦"在社交网络里传播——与本设计几乎一模一样，建议精读其论文。工程侧的参照是 Inworld AI、Convai 这类游戏 NPC 中间件。方向没有问题，真正的约束是三个工程问题：**长程一致性、叙事失重、成本**（第五节给解法）。

另一个好消息：这个世界天然适合该架构。雪国小镇是个**小而稠密的社交网络**（修二、深雪、亲戚群像、鸟羽老人、山/老屋/车站/神社几个场景），比大而空的"开放世界"好做得多。开放世界的开放感不来自地图大小，来自**信息在人物间流动带来的后果感**。

## 二、核心架构（五层）

```
┌─────────────────────────────────────────────────┐
│ 表现层：galgame UI / 立绘 / 打字机 / 存档        │
├─────────────────────────────────────────────────┤
│ 导演层（Director）★人物圣经里没有、但必须有      │
│  · 决定当前场景、在场人物、镜头与节奏            │
│  · 剧情引力：P1~P10 作为"条件触发的稀有事件"     │
│  · 防跑题：玩家闲逛过久 → 推进季节/祭典逼近      │
├─────────────────────────────────────────────────┤
│ Agent 层：每个角色一个 Agent（无状态、纯函数式）  │
│  输入 = 人设卡 + 场景状态 + 记忆检索 + 知识边界   │
│  输出 = 台词 + 动作 + 内部状态增量(情绪/好感/意图)│
├─────────────────────────────────────────────────┤
│ 世界层：事实库(时间/地点/物品/物理常量)           │
│  · 每角色的知识库（谁知道什么、从谁那听来、几手） │
│  · 关系矩阵（数值化好感/信任 + 变更理由）         │
│  · 事件总线（玩家动作 → 事件 → 目击者 → 记忆写入）│
├─────────────────────────────────────────────────┤
│ 护栏层：风格校验器 + 谜团锁校验 + 重试管道        │
│  旁白 Agent（独立于角色，文学化第一人称）         │
└─────────────────────────────────────────────────┘
```

### 2.1 Agent 必须无状态（stateless）

不要给每个角色开一条长对话历史。每次调用 LLM 时，由引擎现场拼装：人设卡（静态）+ 检索出的相关记忆（动态）+ 当前场景 + 该角色的知识边界。这解决三件事：

1. **知识边界防串戏**——深雪就是"看不到"她不该知道的信息，而不是"被要求假装不知道"；
2. **无限长度不崩坏**——记忆在外部数据库，不在 context 里滚雪球；
3. **存档/回放变成免费功能**——事件溯源，重放事件即重建世界。

### 2.2 传播引擎离线模拟，不走完整对话

"传播一遍"不要让 NPC 两两真对话（成本爆炸且玩家看不到）。正确做法：每个游戏日结束时跑一次**八卦模拟**——当 A 和 B 有社交接触（按日程和关系计算），A 以概率把某条信息传给 B，概率和信息是否走样由**性格过滤器**决定。用便宜的小模型甚至纯规则跑，产物是"传闻条目"写进各人知识库。玩家下次和鸟羽老人聊天时才感受到后果："听说……老屋那边，有个不知道哪来的丫头？"——**传播的乐趣在于后果回流到玩家，不在于过程本身。**

用素材举个完整例子：

> 玩家（修二）在亲戚会议上被推诿 → 深雪出现牵走他（P1）→ 事件【雪衣少女出入修二家】进入在场亲戚的知识库 → 数日后亲戚间电话串门，经"拐弯抹角"过滤器传播，扭曲成"老屋那边怕是有点不干净/遗产要出问题" → 鸟羽老人听说后沉默地多看修二几眼 → 某亲戚以"确认遗产安全"为由上门 → 一个没写过的场景自然长出来了。

**这就是"从玩家这个点在社交网络上传播一遍"的实际形态。**

### 2.3 导演层是开放世界不散架的关键

纯涌现的故事是平的、漫游的、没有形状的。人物圣经的 P1~P10 是宝藏：把它们做成**带前置条件的剧情吸引子**——比如 P5（刻身高）的前置条件 = {年末时间窗 ∧ 好感度>阈值 ∧ 地点=老屋 ∧ 提及过父母}。玩家自由行动，但导演持续计算"叙事压力"，在合适的时机把事件推到玩家面前。开放世界 galgame 的正确公式是：**自由度 100% 在过程，骨架仍然是既定时间线。**《塞尔达》也是这么干的。

### 2.4 台词与旁白分离

人物圣经 §5 已经要求，架构上落实为两个 Agent：角色 Agent 被硬约束只输出短句口语；旁白是独立的文学化声音（修二第一人称）。这恰好是防"AI 腔"渗进台词的最有效手段。

## 四、提示词能否完全定制（核心问题解答）

**能，前提是直接调模型 API（GLM、DeepSeek、Qwen、GPT 等的开发者接口），而不是用聊天产品或重型 Agent 框架。** API 的 system 槽位 100% 归你，没有任何隐藏前置词。注意三点：

1. **避开会偷偷注入自己提示词的框架**（某些 Agent 平台会在 prompt 前后塞自己的编排指令）。自己写 prompt 拼装逻辑，框架最多用最薄的 HTTP 封装。控制了拼装逻辑，才控制了每个角色"看到什么"。
2. **诚实的边界**：API 只保证没有*额外的*提示词，但模型训练时固化的行为（助手腔、爱总结、爱圆满收尾）剥不掉，只能压制。压制手段按成本递增：强 few-shot（检索正典台词做示范）→ 低温采样 → 生成后校验+带错误反馈的重试（最多 2 次，仍失败则走规则兜底）→ 最后手段是用《素材文本》语料给深雪做 LoRA 微调。一般到第二档就够了。
3. **一个模型扮演所有角色**，靠不同 system prompt 区分，不要一角色一实例。配合 prompt 前缀缓存（人设卡是静态前缀，可缓存），成本能降一半以上。

## 五、三个必踩的坑（附解法）

### 坑 1：角色坍塌

跑 30 轮后深雪开始说"总的来说""我理解你的感受"。解法：台词引擎规则全部进护栏校验器（称谓白名单、语气词表、禁忌词黑名单、句长上限），违规则重试；正典台词做检索锚点。圣经里"绝无：长句辩护、现代俚语"这类规则天生适合写成校验器。

### 坑 2：谜团泄漏

LLM 有强烈的"解答悬念"倾向，这是纯 prompt 最压不住的东西（尤其玩家反复追问深雪身世时）。必须上**生成后校验**：扫描输出是否触及 §1.3 的四个问题且超出 §2.1 规定的四种合法回应；违规则打回重生成。同时把"修二 T+4 后不再追问"这类设定放进玩家侧引导。这个锁建议做成硬规则而不是软提示。

### 坑 3：叙事失重与成本

纯自由输入 + 纯涌现 = 玩家漂移、无事发生、记忆模糊。解法：

- 导演层的剧情引力 + 时间压力（季节推进、冬祭倒计时）；
- 记忆分层：情景日志 → 每日小模型摘要 → 定期"反思"生成人物洞察（如亲戚们沉淀出"那孩子回来必定是为了老屋"这类信念，反过来影响后续行为）；
- 成本：玩家每回合真实调用约 3~5 次（导演 1 次小模型 + 在场角色 1~3 次 + 偶发旁白），离线传播用小模型或规则，完全可负担。

## 六、落地路线图（别一步到位）

| 阶段 | 内容 | 验证目标 |
|---|---|---|
| **阶段 0**（1~2 周） | 双 Agent 对演原型：无世界、无传播，单场景。深雪 Agent + 修二 Agent 按圣经 §6 的 P1/P7 预设对演，跑自动评测看与正典语料吻合度 | 人设卡+护栏能否立住角色——**立不住就别往上盖楼** |
| **阶段 1** | 加入玩家：玩家替代修二 Agent 自由输入；修二卡退化为旁白声音和 NPC 对玩家的预期模型。加世界事实库 + 单场景记忆 | 玩家自由输入不破坏角色一致性 |
| **阶段 2** | 社交网络：扩到 5~8 个角色（亲戚群像＝性格过滤器各不相同的传播节点群），上知识库、关系矩阵、每日八卦模拟 | 传播产生后果回流 |
| **阶段 3** | 导演 + 剧情引力：P0~P10 做成条件事件，加季节推进、冬祭倒计时 | 自由度与叙事骨架共存 |
| **阶段 4** | 打磨：成本优化、LoRA（如果需要）、演出层（立绘；Ren'Py/Godot/Web 均可，前期用 Web 聊天界面） | — |

**技术栈起步建议**：Python + FastAPI + SQLite（状态）+ 嵌入检索（记忆）+ 任意支持 JSON 结构化输出的模型 API。全链事件溯源存档。
