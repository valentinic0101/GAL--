## 二、最接近论文：One Policy, Infinite NPCs

### 2.1 要解决的问题

逐 NPC 调 LLM 在数百 NPC 规模下延迟与成本爆炸。它让**一个共享策略**驱动成百上千 NPC，同时每个 NPC 保持可辨识的个性。

### 2.2 方法

- 用冻结的 LLM embedding（Qwen3-0.6B）把 NPC **人设文本编码成条件向量**——生成时只算一次；
- 用 FiLM 调制把条件向量注入**单一共享 RL 策略**（PPO + InfoNCE 人设一致性目标 + 多样性 KL 约束）；
- LLM 只负责"读人设、出向量"，不参与逐帧决策——行为由训练好的轻量策略实时产生。

### 2.3 评价所用的技术

- 自建 **300 人设生活模拟基准**：人设零样本识别准确率超随机 **17 倍**、语义-行为对齐相关 ρ≈0.73；
- **效率对比**：比逐 NPC 调 LLM 快约 **22 倍**；
- **工程验证**：UE5 中部署 64 个 agent 实时运行，单决策约 **200 微秒**；
- 三层评测（网格世界诊断/泛化/UE5 实时）+ 消融；
- **局限**：单作者预印本；LLM 只管人设编码不管对话；个性表达靠策略调制，没有真正的语言交互。

## 三、对 GAL 项目的启发

1. **"人设编码一次，处处复用"**：本项目一个模型演所有角色时，人设卡是静态前缀——这篇论文是同一思想的极致版（编码成向量再冻结）。可做的优化：把人设卡 + 常用记忆预编码缓存，运行时只拼动态部分（与架构 V1 的 prompt 前缀缓存建议一致）。
2. **主角例外主义是对的**：该论文证明"原型/共享策略"能撑起群众 NPC，但**对话质量让位了**——galgame 的深雪必须是逐回合真 LLM，亲戚群像可以走"轻量策略/模板+小模型"的群众路线。两档制有了学术背书。
3. **毫秒级预算的参照数字**：UE5 64 agent × 200μs/决策是行业实时底线；Web 版 galgame 远低于此压力，但如果未来接 Ren'Py/Godot 演出层，离线预生成 + 缓存仍是首选。
4. **微软路线的启示**：Xbox×Inworld 说明大厂把"AI NPC"做成中间件而非自研论文——本项目自建引擎的决策，反而符合"控制 prompt 拼装逻辑"的第一性原则。
